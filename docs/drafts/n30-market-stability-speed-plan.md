## 2. 안정성 방안 (S1~S8)

### S1. 장애 복구 시간 단축 — "무커밋 30분 → 사람 호출 → 4시간 내 복구" 절차 고정
- 지금(확정): 헬스 `commitStalled`(F11) + UptimeRobot 3모니터 + 잔존 감사 메일 09:40 하루 1회. 복구는 사람이 윈도우 PS 한 줄·크롬 재시작.
- 할 일: ① UptimeRobot 키워드 모니터를 `"commitStalled":false` 와 `"workerOutdated":false` 두 개로 추가(5분 주기, 앱 푸시). ② 복구 런북 1장(증상 → 명령 한 줄) `docs/` 고정. ③ 월 1회 "윈도우 정지 훈련": 크롬 종료 후 맥 승격까지 분 단위 실측(지금은 승격 규칙만 있고 훈련 기록 없음 — 미확인).
- 위험: 낮음(감시·문서만). 작업: 0.5일(추정).

### S2. 커버리지 자동 집계 + 미달 알림
- 지금: 커버리지는 오늘 백업본을 손으로 계산해야 안다.
- 할 일: DB 함수 `mi_rank_coverage_daily(day)`(활성 추적기 대비 스냅샷 있는 수, 묶음별 마지막 수집 시각) → 헬스에 `coverageYesterday` 정수 1개 + 총관리자 "N 쇼핑 수집 운영" 화면 카드(어제 커버리지·갱신 주기 중앙값·stuck·neverFound·워커 상태). GitHub Actions 09:00 KST: 어제 < 97%면 메일.
- 위험: 낮음(DB 함수 추가만, 수집 무접촉). 작업: 1일.

### S3. 상품 레인 자동 재큐(stuck 자동 복구)
- 지금(확정): 플레이스만 자동 재검증(C3, 하루 ≤10건). 상품 레인은 30분/24시간 주차 후 재시도만 있고, `retry_count 8` 2건은 수동 SQL(`mi_enqueue_naver_shopping_repair_priority`)로만 살아남.
- 할 일: 크론(플레이스 크론 틱 재사용)에서 "retry ≥ 3 이고 마지막 성공 36시간 이상" 상품 추적기를 하루 1회 ≤10건 repair 큐에 자동 인큐 + 감사 기록. 3일 연속 실패면 화면 표식 "구조 점검 필요"로 승격.
- 위험: 중간(DB 함수 호출 추가; 수집기 무접촉). 24시간 관찰 필요. 작업: 1.5일.

### S4. 네이버 구조 변동 카나리아
- 지금(확정): 수집기가 이상 구조에서 fail-closed(1↔2페이지 이음매 등). 감지는 실패 누적 후에야 헬스에 나타남.
- 할 일: 서버가 매 사이클 커밋에서 `checked_count`·광고 수·`total` 분포를 보고, 직전 7일 중앙값 대비 급변(예: checked_count < 300 비율 20%↑)이면 즉시 알림(잔존 감사 워크플로에 항목 추가). 수집기 변경 없음.
- 위험: 낮음. 작업: 1일.

### S5. 런타임 버전 결합 사고 재발 방지(9/1 17시간 정지의 원인)
- 지금(확정): `migration-runtime-literal-audit` 정적 검사 + 범프 체크리스트 문서.
- 할 일: ① `workerOutdated:true` 가 5분 지속되면 UptimeRobot 푸시(S1과 같은 모니터). ② 릴리스 스크립트에 "서버 런타임 버전 변경 커밋은 윈도우 워커 업데이트 완료 확인(지문 일치) 전 main 병합 금지" 게이트(체크리스트 자동화).
- 위험: 낮음. 작업: 0.5일.

### S6. 대기기(맥) 상시성 점검
- 지금(확정): 맥 워치독·FDA 권한·Profile 5 설정이 맞아야 승격 가능. macOS 업데이트로 권한이 사라질 수 있음.
- 할 일: 워치독 틱 로그에 "승격 가능 상태" 1줄(권한·프로필·확장 지문 일치)을 남기고, 헬스에 `standbyReady` 불리언 노출 → 총관리자 카드.
- 위험: 낮음. 작업: 0.5일.

### S7. 데이터 보전
- 확정: 로컬 백업 설치(9/8), 삭제 크론 라이브. 미확인: GitHub Actions 만료 크론 성공 여부.
- 할 일: 매주 월요일 `?dryRun=1` 결과를 메일로 받는 워크플로(삭제 대상 미리보기). Supabase Pro 전환은 대표 결정(자동 백업 7일).
- 작업: 0.5일.

### S8. 수집 품질을 고객에게 보여 주기(안정성의 시장화)
- 광고주 화면 순위 카드 상단에 "어제 수집 성공 n/n · 마지막 갱신 hh:mm" 한 줄. 누락이 있으면 "재수집 예정"으로 정직하게 표시.
- 근거: 안정성이 좋아도 고객이 모르면 시장성이 안 된다. S2 집계값 재사용.
- 작업: 0.5일.

## 3. 속도 방안 (P1~P6)

### P1. 사이클 간격 10분 → 5분 (한 바퀴 11시간 → 5.5시간)
- 확정: 간격은 확장 baseline 상수(수집기 런타임) → 변경 = 런타임 인상 1회(서버·DB·윈도우 워커 동반, 정지 창 절차).
- 추정: 페이지 로드가 70초당 1건에서 35초당 1건으로 늘어남. 네이버 418/429 쿨다운 이력은 미확인 — 인상 전 최근 30일 쿨다운 발생 횟수를 DB에서 세어 근거로 삼는다.
- 효과: 갱신 주기 9시간 → 4.5시간, 신규 키워드 ≤ 5분, 단일 워커 용량 288묶음.
- 위험: 중간(차단 위험은 실측 전 추정). 작업: 1.5일 + 정지 창 1시간 + 24시간 관찰.

### P2. 우선순위 큐 — "변동 큰 키워드·신규·고객 요청" 먼저
- 지금(확정): 순차 커서 1개. 계정 우선(one-shot)은 총관리자 조작.
- 할 일: 사이클 선택 함수에 가중치(신규 > 어제 미수집 > 순위 변동폭 큰 순 > 나머지). DB 함수 변경, 수집기 무접촉.
- 효과: 같은 속도로 "고객이 보는 체감 신선도" 상승.
- 위험: 중간(사이클 선택 로직은 잠금 영역 — 대표 승인 필요). 작업: 2일 + 24시간 관찰.

### P3. "매일 아침 확정 순위" 보장(마케팅 약속으로 쓰는 속도)
- 밤 00:00~07:00에 전 묶음 1바퀴를 반드시 마치도록(트래픽 적은 시간) 사이클 밀도를 높이고, 화면에 "오늘 확정 순위(07:00 기준)"와 "최신 갱신"을 나눠 표시.
- 확정: 지금은 하루 종일 균등 분포(00~23시 스냅샷 수 거의 같음). 65묶음×5분 = 5.4시간이면 야간 1바퀴 가능.
- 작업: P1 뒤 1일.

### P4. 병렬 워커(샤딩) — 용량 300묶음 넘을 때
- 확정: 지금 설계는 "주 작업기 1대 + 대기기"(동시 2대 금지). 코호트·리스·계정 우선 함수가 단일 주 작업기를 전제.
- 할 일(장기): 묶음을 해시로 2개 코호트에 나눠 윈도우·맥이 각자 코호트만 수집, 대기 승격 규칙을 코호트별로. DB 함수·확장 모두 변경.
- 위험: 높음(N30 핵심 구조). 용량이 실제로 부족해질 때(활성 200묶음↑) 착수. 작업: 5일+.

### P5. 서버 폴백 승격(모바일 상위 50)
- 확정: 폴백 44건/30일. 워커 정지 시 폴백이 상위 50위만 채움.
- 할 일: 워커 무커밋 30분 지속 시 서버 폴백을 전 묶음에 하루 1회 자동 실행(상위 50위라도 기록 유지, `source` 로 구분 표시). 장애 중 커버리지 0% → 상위권 상품은 유지.
- 위험: 중간(네이버 모바일 호출량 증가). 작업: 1일.

### P6. 화면 속도
- 확정: 총관리자 1.2MB·광고주 674KB 단일 HTML, `no-store`, 인라인 스크립트(CSP 해시 관리 부담).
- 할 일: ① 모바일 Lighthouse 실측(기준선) ② 순위 화면 스크립트를 외부 파일로 분리해 `immutable` 캐시(버전 쿼리) — 해시 갱신 부담도 사라짐 ③ 30일 스냅샷은 화면이 원본 행을 받지 말고 서버 집계(추적기별 30일 배열 1개)로 ④ 순위 목록 API 응답 크기 실측 후 필요 시 페이지네이션.
- 위험: 중간(client/admin 대형 파일 리팩터, 잠금 함수 포함 가능). 작업: 3일.

## 4. 시장성 방안 (M1~M8)

### M1. 약속을 숫자로 — "매일 아침 확정 순위 · 30일 기록 · 성공률 공개"
- S2·S8·P3 결과를 홈·요금 안내에 그대로 씀. 경쟁 제품 대비 차별점은 "원부(카탈로그) 기준 순위"와 "300위까지"(확정: 8페이지×40).
- 작업: 문구·홈 1일(수집 무접촉).

### M2. 순위 변동 알림(고객 재방문·유료 전환의 핵심)
- 조건: 1페이지 진입/이탈, N위 이상 하락, 300위 밖 이탈, 3일 연속 미수집.
- 채널: 1단계 이메일(구글 연동 계정은 이메일을 이미 앎 — 확정: `login_identities.google_email`), 2단계 카카오 알림톡(비즈 채널·템플릿 심사 = 대표 작업, 미확인 소요).
- 구현: 스냅샷 커밋 후 서버 규칙 평가 → `notifications` 표 + 하루 1회 묶음 발송. 이메일 발송 서비스 선택 필요(대표 결정: 예 Resend/SES, 월 비용 소액 추정).
- 작업: 3일.

### M3. 주간 리포트 자동 발송
- 확정: 이미지 저장(요약 PNG·데이터 캡처)은 이미 있음. 매주 월요일 광고주별 30일 순위 이미지 + 요약 3줄을 메일로.
- 작업: M2 발송 기반 위에 1.5일.

### M4. 경쟁 상품 30일 변동 화면 — 추가 수집 없음
- 확정: 매 스냅샷에 상위 5개 상품(몰·브랜드·가격·광고 여부)이 이미 저장됨(`top_items`). 30일치로 "상위 5 진입/이탈·가격 변동·광고 비중"을 그릴 수 있음.
- 홈 "내 키워드 지표"와 순위 카드에 "경쟁 상위 5" 탭. 체험 계정 예시 데이터에도 포함.
- 작업: 2.5일(화면·집계 RPC).

### M5. 체험 확장 — "순위 추적 3개 · 7일"
- 확정: 지금 체험은 키워드 조회 5회/일뿐, 순위는 예시 데이터. 용량 여유(65묶음/288)로 체험 3묶음 × 동시 20명도 감당(추정).
- 규칙: 체험 추적기는 코호트 최하 우선순위(P2), 7일 후 자동 일시중지, 전환 시 유지.
- 잠금 영역(세션 게이트·추적기 API) 변경 → 대표 승인 필요. 작업: 3일.

### M6. 등록 UX — 미발견 절반 줄이기
- 확정: 미발견 10건 대부분 실제 300위 밖 또는 원부 묶임. 등록 시 서버가 URL로 원부 여부 판별해 "원부 기준으로 등록됨/판매처 기준" 표시, 300위 밖은 "300위 밖(추적 중)"으로 명시.
- 작업: 1일.

### M7. 플레이스 순위 상품화
- 확정: 16개, 누락 4.9%, 외부 수집기(Render/Playwright), 하루 약 2회. 상품 레인 S1~S3 안정화 뒤 요금제에 명시.
- 작업: 별도 기획.

### M8. 요금제·전환 경로 정리
- 확정: 플랜(basic/premium/custom), 추적 한도 50, 구글 연동 기한 10/7, 결제 수기. 광고주 8곳 중 2곳이 추적기 62개 → 사용량 편차 큼.
- 제안: 추적 묶음 수 기준 3단계(예 10/30/100묶음) + 알림·리포트는 상위 단계. 가격은 대표 결정. 셀프 결제(토스페이먼츠 등)는 후순위.
