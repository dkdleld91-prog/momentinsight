# Decisions

## 2026-08-10 · Windows 작업용 데스크탑은 사용자 범위 브리지로 운영한다

- Windows Chrome의 확장 관리 화면이 비어 있는 것은 macOS 전용 브리지가 자동 이전되지 않았기 때문이다. Windows는 전용 `프로그램 개발` 프로필을 만들고 압축해제 확장을 한 번 직접 로드한다.
- Native Messaging host는 Chrome 공식 `HKCU\\Software\\Google\\Chrome\\NativeMessagingHosts` 경로에 현재 사용자 범위로 등록한다. 고정 확장 ID 하나만 `allowed_origins`에 허용한다.
- 운영 워커 비밀키는 명령줄·평문 설정·확장에 넣지 않고 Windows 현재 사용자 DPAPI로 암호화한다. 다른 Windows 사용자나 복사된 파일만으로는 복호화할 수 없게 한다.
- Chrome은 로그인 사용자 전용 작업 스케줄러가 로그인 직후와 10분 간격으로 `프로그램 개발` 프로필만 확인한다. 관리자·SYSTEM 비대화, 원격 디버깅, sandbox 해제, CAPTCHA 우회는 사용하지 않는다.
- Windows에서 신규 원자 300개 실증 전에는 기존 Mac을 대기 안전망으로 유지한다. 실증 뒤에는 Windows만 주 작업자로 두고 두 장비의 중복 브라우저 요청을 만들지 않는다.

## 2026-08-08 · Codex 업무 역할을 개발·제품 이사로 고정한다

- 프로젝트 운영상 Codex의 역할명을 `모먼트 인사이트 개발·제품 이사`로 사용한다. 이는 법적 임원·대표권·결제 권한이 아니라 개발·제품·UI/UX 품질을 대표님과 공동으로 책임지는 역할이다.
- 승인된 작업은 현상 확인, 원인 확정, 최소 범위 구현, 대상 테스트, 역할·기능 2차 회귀검수, 문서화, 승인 시 배포, 운영 확인을 종료 기준으로 삼는다.
- 실증 없는 완료·정상화·배포 보고를 금지한다. 대표님만 처리할 수 있는 로그인·보안확인·결제·외부 승인이 남으면 차단 원인과 다음 한 가지 행동을 기록하고 이후 즉시 속행한다.
- 제품 방향, 결제·유료 자원, 운영 데이터 삭제, 외부 전송, 최종 배포의 결정권은 대표님에게 유지한다.

## 2026-08-09 · 24시간 보호 대기를 없애고 당일 전체 순환을 우선한다

- 오전 9시·오후 3시는 광고주가 갱신 시점을 이해하기 위한 화면 안내와 다음 갱신 표시에 유지한다. 내부 300위 수집의 시작·종료를 두 시각에만 묶지 않는다.
- 개발 Chrome의 20분 `rank-catch-up` 회차마다 사이트 전체 `status=active` 추적을 멱등 방식으로 대기열에 확인 등록한 뒤, 가장 오래 기다린 키워드 1개만 순차 수집한다.
- 이미 due인 행과 처리 중 lease는 다시 쓰지 않아 중복 행·대기 순서 변경을 만들지 않는다. 직전 성공으로 미래 예약된 행만 다음 회차에 대기열 뒤로 다시 들어가 전체 목록이 계속 순환한다.
- 2026-08-09 운영 읽기 기준 활성 59건·고유 키워드 47개이므로 오류가 없을 때 약 15시간 40분에 한 바퀴다. 처리량을 높이기 위한 동시 브라우저 수집은 사용하지 않는다.
- 네트워크 제한·418·429는 `30분 → 60분 → 120분`으로 재시도하고 이후에도 120분을 상한으로 유지한다. CAPTCHA·보안확인은 자동 우회하지 않으며 사람이 정상 화면을 확인하면 1건부터 재개한다. 실패 작업과 미처리 작업은 마지막 정상값·30일 이력을 보존하고 기존 oldest-first 순서로 이어간다.

## 2026-08-08 · Mac 수집 상한을 2건으로 복귀하고 확인 해결 전 job claim을 금지한다

- 4건 설정의 첫 운영 실행은 첫 작업에서 기존 네이버 보안확인을 감지해 실제 4건 연속 수집에 도달하지 못했습니다. 안전성이 검증된 회차당 순차 2건을 다시 기본값으로 사용합니다.
- 저장된 보안확인 탭이 blocked/unknown이면 자동·수동 실행 모두 native host 연결과 서버 job claim 전에 중단합니다. 확인 화면을 자동으로 우회하거나 새 탭으로 반복 요청하지 않습니다.
- 사용자가 확인을 완료해 정상 쇼핑 `__NEXT_DATA__`가 나타나면 다음 실행이 상태를 자동 해제하고 2건 안전 수집을 재개합니다.
- 전체 갱신 멱등화, oldest-first, 조건부 lease와 300개 원자 저장은 그대로 유지하므로 처리량 복귀가 중복 등록이나 광고주 간 순서 변경을 만들지 않습니다.

## 2026-08-08 · Mac 수집은 4건 순차 처리하고 전체 갱신은 멱등화한다 (운영 관찰 후 상한 결정 폐기)

- 광고주 증가에 대응해 중앙 Mac의 10분 회차 상한을 2건에서 4건으로 올리되 브라우저 병렬 실행은 하지 않습니다.
- 페이지 간 3.5~6초 분산, 보안확인·418·429 즉시 중단, 1시간 쿨다운, 마지막 정상값·30일 이력 보존을 처리량보다 우선합니다.
- 계정별·사이트 전체 갱신은 이미 due인 tracker를 다시 쓰지 않습니다. 반복 클릭은 새 행을 만들거나 대기 시각을 갱신하지 않고 `alreadyQueued`로 집계합니다.
- 중앙 claim의 oldest-first와 조건부 lease를 유지해 한 광고주의 반복 요청이 다른 광고주의 기존 대기 순서를 밀어내지 않게 합니다.
- 서버 코드와 중앙 Mac 설치본은 검증 완료 및 사용자 승인 후 같은 릴리스로 반영합니다.

## 2026-08-03 · 담당자 수동 1회로 사이트 전체 활성 추적을 등록한다

- 네이버 쇼핑 검색 API와 공식 대체 API가 모두 없는 현재 운영에서는 중앙 Mac 확장을 실수집 진입점으로 유지한다.
- 확장의 수동 실행만 사이트 전체 `status=active` 추적을 현재 due로 등록한다. 계정별 선택이나 코드 열거 없이 HMAC·nonce 경계 안에서 처리하고, 신규·미도래 항목도 같은 기준으로 포함한다.
- 한 번에 전체 브라우저 수집을 몰아 실행하지 않는다. 첫 회차 최대 2건 뒤 기존 10분 catch-up이 남은 due를 처리하고, 보안확인·418·429는 1시간 휴지한다.
- 처리 중 lease, 마지막 정상 순위, 기존 30일 snapshot, 정확 상품·원부 판정, 광고 제외, 300개 원자 저장 계약은 변경하지 않는다. 서버와 중앙 Mac 설치본·확장 버전은 반드시 같은 릴리스로 순서대로 반영한다.

## 2026-08-02 · 종료 쇼핑 API를 계승하지 않는 hybrid 원자 수집 경계

### 새 인증값을 과거 페이지 계약에 끼워 넣지 않는다

- 2026-07-31 종료된 쇼핑 상품 검색 API의 1·101·201 페이지 응답과 새 Naver API Hub 인증은 서로 다른 제품 계약이다.
- 공식 Hub에 상품 검색 결과 대체 API가 없으므로 URL·헤더만 바꾸거나 Search Trend·Shopping Insight·Commerce API를 오가닉 순위로 해석하지 않는다.
- 키워드 상품 참고값과 N 상품 단건·30일 순위는 하나의 `mi.naver-shopping-organic-window.v1`만 소비한다.
- 유료 외부 수집기는 사용하지 않는다. 향후 별도 공급자를 검토하더라도 동일한 광고 제외·정확 ID·원자 300개 계약을 먼저 통과해야 한다.

### 순위는 한 시점의 검증된 원자 목록에서만 계산한다

- 300위 워커의 성공 결과는 하나의 `collectionId`·`collectedAt`과 오가닉 1~300위의 연속 순번을 갖는다. 서버 상위 50위 경로는 확인 범위 밖을 완전 수집으로 가장하지 않는다.
- 광고, 중복 stable ID, 혼합 source/evidence, 부분 목록, 잘못된 exact/catalog 관계가 있으면 전체 결과를 폐기한다.
- 불완전 조기 일치도 현재 순위·snapshot·30일 이력을 덮지 못한다. 마지막 정상값을 유지하고 재검증 대상으로 남긴다.

### 서버 상위 50위와 일반 Chrome 최소권한 300위를 분리한다

- 서버 즉시 경로는 모바일 통합검색의 명시적 SAS 상품 슬롯에서 광고를 제외하고, 1위부터 연속 검증된 최대 상위 50위의 exact ID만 확정한다.
- 상위 50위 밖의 미발견은 `없음`으로 저장하지 않는다. 마지막 정상 순위와 30일 이력을 유지한다.
- 정확한 1~300위 수집은 사용자가 명시적으로 승인한 일반 `동빈` Chrome의 최소권한 확장 프로그램으로 수행한다. 확장은 공개 쇼핑 검색 DOM의 `__NEXT_DATA__`만 읽고 cookies·history·webRequest 권한을 요청하지 않는다. 비밀번호·쿠키 전송과 CAPTCHA 자동 우회는 허용하지 않는다.
- 로컬 워커는 HMAC 서명·제한된 유효시간·1회용 nonce를 사용하고, 검증된 300개를 tracker와 snapshot에 원자 반영한다. 부분·중복·lease 상실 결과는 전체 거부한다.
- 해당 Mac 또는 Chrome이 꺼져 있으면 새 51~300위 증거는 만들 수 없다. 이때도 서버 상위 50위 경로와 기존값 보존 안전망은 계속 동작하며, 다음 시작 시 due tracker를 따라잡는다.

### 순위 진실과 부가 상품수는 서로의 가용성을 막지 않는다

- 순위 필수 계약은 오가닉 문서 순서, 광고 제외, 고유 identity, 완주 범위, `collectionId`·`collectedAt`이다.
- 전체 상품수는 `marketTotalStatus=verified`일 때만 경쟁강도 계산에 사용한다. 문구 누락·페이지별 변경·수집량 미만이면 `marketTotal=null`, `marketTotalStatus=unavailable`로 두고 순위와 상품 표본은 유지한다. 수집 개수를 전체 상품수로 대체하지 않는다.
- HTTP 418·429, CAPTCHA, 인증 전환, selector drift, deadline, 부분 수집은 fail-closed 처리하고 기존값을 보존한다.
- 오전 9시·오후 3시는 로컬 워커 우선 실행 창이다. 뒤따르는 재시도와 매시 안전 실행은 남은 due tracker를 처리하되, 검증되지 않은 값을 성공으로 만들지 않는다.

### 무과금 경계와 실수집 증거를 분리한다

- 유료 수집 서비스·유료 plan·카드·자동 결제는 추가하지 않는다.
- 단위·계약 테스트 통과는 실수집 증거가 아니다. `collection_id=pw-*`, `checked_count=300`인 최근 snapshot과 광고 제외·연속 순번·정확 상품/원부 일치를 확인하기 전에는 300위 정상화나 Production 반영 완료로 기록하지 않는다.

> 아래 2026-07-31 이전의 공식 쇼핑 검색 API 순번 관련 결정은 당시 운영 이력이다. 현재 런타임 순위 계약과 충돌하면 위 2026-08-02 hybrid 원자 수집 결정이 우선한다.

## 2026-07-14 · 운영 수치와 광고주 빈 상태를 실제 데이터 기준으로 표시

### 실집계 전 숫자와 예시 브랜드를 운영 현황으로 사용하지 않는다

- 운영 홈의 정적 `12개·4건·3건·2건`과 브랜드 예시 목록은 실제 계정 상태처럼 오해될 수 있어 제거한다.
- 실집계 API가 연결되기 전에는 계정 연결, 운영 입력, 공개 승인, 보고서 관리로 이동하는 작업 카드를 제공한다.
- 오래된 업데이트 날짜와 담당자 예시 대신 공개 저장 시 기록되는 원칙과 현재 접속 권한 범위를 표시한다.

### 광고주 빈 상태와 공개 완료 상태를 분리한다

- 매출·ROAS·광고비·구매수·달성률이 모두 비어 있으면 `공개 준비 중`, `공개 데이터 연결 대기`, `운영팀 공개 입력 전`으로 표시한다.
- 공개 데이터가 있으면 기존 `업데이트 완료`, `운영팀 검수 완료`, `공개용` 상태를 유지한다.
- 보고서 렌더링은 저장소를 다시 읽지 않고 현재 상태의 `reportCenterSynced`를 직접 사용해 빈 상태에 데모 보고서가 혼입되는 경합을 막는다.
- 모바일 빈 상태는 중복 판단 영역을 숨기고 핵심 지표와 두 개의 액션만 남겨 카드 높이를 줄인다.

### 역할 공통 메뉴 전환은 화면 상단에서 시작한다

- 운영팀과 광고주 모두 메뉴 클릭 후 스크롤을 0으로 복귀시켜 새 화면이 중간부터 열리지 않게 한다.
- 릴리즈 기준선에서 가짜 운영 집계 제거, 빈 상태 마커, 보고서 상태 전달, 공통 스크롤 복귀를 검사한다.

## 2026-07-14 · 판매자 상품번호와 API 상품번호 분리

### 판매자 상품은 결과 링크의 상품번호로만 확정한다

- 네이버 쇼핑 검색 API의 `productId`는 검색 항목 식별자이고 판매자 상품 페이지 번호와 다를 수 있다.
- 판매자 상품 URL 조회에서는 API `productId`가 입력 번호와 우연히 같아도 정확 상품으로 처리하지 않는다.
- 결과 링크의 `/products/{id}` 또는 정규 URL이 입력 대상과 일치할 때만 `seller_link_product_id` 근거로 확정한다.
- 명시적 원부 조회는 별도 `catalog_id` 근거를 사용해 판매자 상품 판정과 섞지 않는다.

### 첫 일치 뒤에도 요청 범위를 끝까지 확인한다

- 300위 조회에서 정확 상품을 173위에 찾았더라도 300개 오가닉 슬롯까지 계속 수집한다.
- 공식 API 제공 순서를 순위 근거로 유지하며 임의 중복 제거로 순번을 재계산하지 않는다.
- 정확 상품 카드의 상세 링크는 입력한 원본 상품 URL로 고정하고 API가 반환한 링크는 검증 근거로만 보관한다.

- 네이버 실화면의 `product` 순번과 별도 삽입 타입을 구분하고 `product` 오가닉 순번만 페이지·순위 기준으로 사용한다.

### 추적과 저장 단계에서 다시 검증한다

- 대표 원부·정확 상품 선택 전에 광고 후보를 제거하고, 광고 후보만 남으면 순위 없음으로 처리한다.
- 수동 갱신·자동 크론은 같은 `runTrackerCheck` 경로를 사용하며 새 스냅샷의 대표 항목과 `top_items`도 오가닉만 저장한다.
- 새 스냅샷에는 `rankPolicy=organic_only`, `adExcluded=true`, 제외 개수를 기록한다. 과거 기록은 근거 없이 소급 변경하지 않는다.
