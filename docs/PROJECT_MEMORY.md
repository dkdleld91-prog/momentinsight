## 네이버 상품 순위 고정 기준

- 현재 상품 순위 원천은 종료된 쇼핑 검색 API나 NAVER API Hub가 아니라 `hybrid_local_worker` 경계다. Hub에는 전체 쇼핑 오가닉 순위를 반환하는 공식 endpoint가 없으므로 Search·Search Trend·Shopping Insight·Commerce API를 순위로 해석하지 않는다.
- 서버는 명시적 SAS 상품의 광고 제외 연속 상위 50위 안 exact hit만 즉시 확정한다. 범위 밖 miss는 `없음`으로 저장하지 않고 마지막 정상 순위와 30일 이력을 보존한다.
- 정확한 1~300위는 사용자가 승인한 일반 `동빈` Chrome의 최소권한 MV3 확장에서 공개 쇼핑 페이지 `__NEXT_DATA__`만 읽어 수집한다. cookies·history·webRequest 권한, 비밀번호·쿠키 서버 전송, CAPTCHA 자동 우회는 허용하지 않고 HMAC 비밀값은 macOS 키체인에만 둔다.
- 300위 워커 응답은 하나의 `collectionId`·`collectedAt`과 연속된 오가닉 1~300위를 가져야 한다. HMAC·유효시간·1회용 nonce·lease를 통과한 결과만 DB에서 원자 반영하며 부분 응답, 혼합 출처, 순번 불연속, 중복 stable ID는 전체 폐기한다.
- 광고 판정은 수집 문서의 명시적 `adId`와 광고 타입만 사용한다. 광고 제거 전후 개수를 계약으로 검증하고 새 스냅샷에는 `rankPolicy=organic_only`, `adExcluded=true`를 남긴다.
- 수집기가 확정한 오가닉 순번에서 `page=ceil(rank/40)`, `position=((rank-1)%40)+1`, `pageSize=40`을 파생한다. 이는 개인화된 사용자 화면을 별도로 검증했다는 뜻이 아니므로 `webPageVerified=false`를 유지한다.
- 판매자 상품 URL은 수집 결과 링크 `/products/{id}`의 판매자 상품ID를 최우선 정확 일치 키로 사용한다. 수집 항목 ID와 판매자 상품ID를 같은 값으로 추정하지 않는다.
- 정확 상품을 먼저 찾더라도 요청 범위를 끝까지 확인해 관련 원부와 누락 후보를 함께 수집하며, 완주 근거가 없으면 성공 처리하지 않는다.
- 관련 원부는 키워드, 브랜드·제조사·판매처 중 하나, 상위 카테고리 2단계가 모두 맞는 가격비교 원부 중 가장 높은 1건만 인정한다.
- 단건과 30일 추적 모두 정확 상품과 검증된 관련 원부 중 숫자가 더 낮은 오가닉 결과를 대표 `rank`, `page`, `position`, 상품 형태로 사용한다. 원부가 높으면 `원부형`, 정확 상품이 높거나 같으면 해당 상품 형태를 표시한다.
- 대표값이 원부여도 `targetProductId`, 입력 URL, 정확 상품 판매자ID는 변경하지 않는다. `representativeItem`과 `exactItem`을 분리하고 카드 2건을 함께 제공한다.
- 같은 원부의 다른 판매자 상품, 같은 판매처의 무관 상품, 브랜드·카테고리가 다른 원부는 정확 상품 또는 대표 원부로 처리하지 않는다.
- 상품명은 조회 키워드의 네이버쇼핑 검색 결과로, `상품 열기`는 원부 카탈로그 또는 사용자가 입력한 정확 상품 URL로 연결한다.
- 관련 원부 배지는 네이버 민트·그린, 정확 상품은 딥네이비를 사용하고 두 역할에서 동일한 컴팩트 카드 레이아웃을 유지한다.
- 광고 순위·광고 개수는 오가닉 순위와 섞지 않고 `광고상품 미연결`로 남긴다.
- 오전 9시·오후 3시는 광고주 화면의 신뢰 가능한 갱신 안내로 유지하되 내부 300위 수집은 두 시각에 종속하지 않는다. 개발 Chrome은 20분마다 사이트 전체 활성 추적을 멱등 확인 등록하고 oldest-first로 키워드 1개씩 계속 순환한다. Mac이 꺼져 있으면 새 51~300위 증거는 만들 수 없지만 서버 상위 50위와 기존값 보존은 계속된다.
- 담당자가 확장의 `지금 안전 갱신`을 누르거나 웹에서 원격 wake를 보내도 같은 HMAC·nonce·lease 경계를 사용한다. 수동 전체 갱신은 전체 활성 목록을 등록하고, 원격 wake는 최대 1건만 실행하며 남은 항목은 20분 전체 순환 회차가 이어 처리한다. 네트워크 제한·418·429는 30분·60분·120분 뒤 재시도하고 이후에는 120분을 상한으로 유지한다.
- 유료 외부 수집기·카드·자동 결제는 사용하지 않는다.
- 코드·계약 검사와 브라우저 육안 확인은 DB 반영 증거가 아니다. 최근 `collection_id=pw-chrome-*`, `checked_count=300` snapshot이 확인될 때까지 300위 실수집 정상화와 Production 배포는 대기 상태로 기록한다.
- 과거 30일 기록은 당시 원부 순번 원본이 없으면 소급 변경하지 않고 새 갱신부터 대표 기준을 적용한다.
- 네이버 Developers 쇼핑 검색 API는 API Hub 이관 제외 상태로 2026-07-31 종료됐다. 종료 API와 새 Hub 키는 순위 fallback으로 사용하지 않으며 수집 계약이 검증되지 않으면 마지막 정상 기록만 보존한다.

## 네이버 키워드 연령 비중 고정 기준

- 쇼핑인사이트 키워드 연령 API의 `ratio`는 절대 검색량이나 장기 구성비가 아니라 각 조회 구간에서 최고 연령을 100으로 둔 상대 클릭지수다.
- 월별 상대지수는 월마다 분모가 달라 전체 클릭량 가중치 없이 여러 달을 단순 합산하지 않는다.
- 연령별 차트는 최신 완료 월의 같은 구간만 사용해 10·20·30·40·50·60대 값을 합계 100%로 정규화하고, 50·60대는 `50대 이상`으로 합친다.
- 진행 중인 월은 제외한다. API가 클릭 0인 연령 행을 생략하면 0%로 처리하고, 완료 구간이 없으면 비율을 만들어내지 않는다.
- 서버 응답은 `ageBasis=latest_complete_month_shopping_keyword_share`와 `agePeriod`를 남기며 운영팀·광고주 화면은 `연령별 쇼핑 클릭 비중`으로 동일하게 설명한다.

## 네이버 플레이스 순위 고정 기준

- 플레이스 ID가 URL에 있으면 상호명 유사도보다 ID 일치를 우선한다.
- 운영 순위는 네이버 PC 실제 장소 목록에서 직접 확인한 광고 제외 오가닉 행만 사용한다. `source=naver_map_pc_list_collector`, `rankEvidence=naver_pc_organic_list`가 모두 없으면 서버가 저장을 거부한다.
- 네이버가 키워드 유형에 따라 만든 네이티브 목록 경로를 보존한다. 특히 의료 검색의 `hospital/list`는 `display=70` 문맥을 강제로 300으로 바꾸면 빈 일반 `place/list`로 리디렉션되므로 원본 경로·검색 파라미터를 그대로 사용한다. 맛집의 `restaurant/list`는 기존 300개 확장을 유지한다.
- Apify 결과 배열은 실제 PC 목록과 다를 수 있어 운영 순위 근거로 사용하지 않고 진단용으로만 유지한다.
- `checkedCount < 300`인 미발견 결과는 300위 밖으로 확정하지 않고 확인 범위 이후를 미검증으로 남긴다.

## 지속 개발 운영 계약

- 시작할 때 Git 상태, 최근 커밋, 작업명세, 현재 상태, 다음 작업을 읽고 `npm run work:autosave`를 실행한다.
- 기존 구현·문서·테스트를 먼저 검색해 같은 기능과 파일을 다시 만들지 않는다.
- 사용자의 미커밋 변경과 관련 없는 diff는 보존한다. 특히 `admin.html`과 `client.html`은 한쪽 변경이 다른 쪽의 기능·권한·레이아웃을 깨지 않는지 함께 확인한다.
- 변경은 작고 되돌릴 수 있는 논리 단위로 나누며, 각 단위의 목적·검증·결과를 작업명세와 운영 문서에 남긴다.
- 완료 전 대상 테스트, 다른 관점의 2차 검증, `git diff --check`, 최종 diff와 상태 확인을 수행한다.
- 검증된 논리 단위마다 로컬 커밋해 다음 작업의 기준점을 만든다. 비밀값, 임시 파일, 재생성 산출물은 커밋하지 않는다.
- 외부 한도나 계정 문제로 핵심 실검증이 불가능하면 보류 상태와 재개 조건을 기록하며, 완료·정상화·배포로 처리하지 않는다.
- push와 배포는 현재 작업에서 명시된 승인 범위 안에서만 수행하고, 승인 이후에도 필수 검증 실패 시 중단한다.

## 역할 공통 사이드바 UI 기준

- 운영팀과 광고주 사이드바는 `운영 → 키워드·SEO → 순위 조회·추적 → 광고 조사` 네 개 메뉴 분류를 공통으로 사용한다.
- 역할별 기능과 권한은 유지하되 사이드바 폭, 브랜드 마크, 그룹 제목, 메뉴 간격, hover·active 상태, 인증 패널의 시각 체계는 동일하게 유지한다.
- 광고주는 운영 기능을 추가로 받는 것이 아니라 본인에게 허용된 대시보드, 매출, 일정, 대행사 연결과 마케팅 도구만 공통 분류 안에 표시한다.
- 데스크톱은 고정 사이드바, 모바일은 상단 가로 스크롤 메뉴를 사용하며 390px에서 문서 전체 가로 넘침이 없어야 한다.
- `data-mi-shell="premium-sidebar"`와 릴리즈 기준선 검사로 두 역할의 공통 쉘 누락을 방지한다.

## 대시보드 상태 진실성 기준

- 운영 홈에는 DB·API에서 실제 집계하지 않은 광고주 수, 누락 건수, 승인 대기 건수나 예시 브랜드를 운영 수치처럼 표시하지 않는다.
- 실집계가 연결되기 전에는 계정 연결, 운영 입력, 공개 승인, 보고서 관리로 이동하는 작업 카드만 제공한다.
- 광고주 공개 데이터가 비어 있으면 `업데이트 완료`, `검수 완료`, `공개용`으로 표시하지 않고 `공개 준비 중`, `공개 데이터 연결 대기`, `데이터 대기`로 명확히 구분한다.
- 빈 공개 상태에서 기본 데모 보고서가 섞이지 않도록 현재 `reportCenterSynced` 상태를 보고서 렌더러에 직접 전달한다.
- 운영팀·광고주 메뉴 전환 시 이전 화면의 스크롤 위치를 유지하지 않고 새 화면의 상단 제목부터 보여준다.
- 390px 광고주 빈 상태는 핵심 지표 3개와 오늘 결론·다음 행동을 한 화면에 가깝게 압축하고 문서 가로 넘침이 없어야 한다.

## 의료 플레이스 네이티브 목록 지연 기준

- 의료 등 카테고리 검색은 네이버가 생성한 네이티브 목록 프레임을 반드시 확보한 뒤 수집한다.
- 느린 환경에서는 20초 대기와 1회 재시도를 허용하지만, 네이티브 목록이 없으면 일반 `place/list`로 폴백하지 않고 `naver_map_native_list_frame_not_found`로 실패한다.
- 정확 플레이스 ID, `source=naver_map_pc_list_collector`, `rankEvidence=naver_pc_organic_list`가 함께 확인된 순위만 저장한다.
